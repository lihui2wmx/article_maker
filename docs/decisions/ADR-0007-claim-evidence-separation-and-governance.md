# ADR-0007 — Separate evidence records from governed claim interpretation

**Status:** Accepted  
**Date:** 2026-09-02  
**Phase:** 3A — typed Claim/Evidence contracts

## Context

Phase 3 introduces the scientific-state layer that connects research questions and hypotheses to manuscript-ready scientific claims. The design must represent both traceable evidence and the interpretation that an item of evidence supports or contradicts a claim.

Those are different epistemic objects:

- an `Evidence` record says that some traceable material exists and describes what was observed, derived, or stated;
- a relation such as “this evidence supports Claim X” is an interpretation of that material;
- a `Claim` is a substantive scientific assertion that may later appear in reasoning or manuscript prose.

The project charter requires humans to retain authority over substantive scientific claims and materially ambiguous interpretation. A representation that stores support/contradiction directly inside Evidence would allow evidence ingestion or extraction code to silently promote interpretation into canonical scientific state.

## Decision

### 1. Keep Claim, Evidence, and ClaimEvidenceLink as separate canonical object types

Phase 3A defines:

- `Claim` (`clm-*`): a scientific assertion attached to a ResearchQuestion and optionally a Hypothesis;
- `Evidence` (`ev-*`): a provenance-bearing record of observed/generated/literature/theory material;
- `ClaimEvidenceLink` (`cel-*`): an explicit interpretation that one Evidence record `supports` or `contradicts` one Claim.

The graph relation is therefore represented as first-class repository state rather than inferred from prose or embedded inside the Evidence object.

### 2. Evidence records are provenance-bearing but not “approved”

Evidence has no approval lifecycle in schema version 1.0.

An Evidence record must have at least one repository Artifact source, optionally with a locator into that artifact. It records what material is available and where it came from; it does not declare that the material is sufficient, correct, or supportive of any specific Claim.

This prevents an operational ingestion status from being confused with scientific endorsement.

### 3. Claim approval is human-governed

Claims use lifecycle states:

- `candidate`
- `approved`
- `rejected`
- `superseded`

A candidate Claim must not carry a governing Decision. Every non-candidate state requires an explicit human `Decision` reference.

Agents may propose Claims but may not independently create canonical approved Claims.

### 4. Claim–Evidence interpretation is independently governed

ClaimEvidenceLink uses:

- relation: `supports | contradicts`;
- lifecycle: `proposed | accepted | rejected | superseded`.

A proposed link may be generated by an agent or human. A non-proposed link requires a human Decision.

This is intentionally stricter than merely storing evidence beside a claim: the scientific interpretation itself is auditable and governed.

### 5. Reuse the existing generic Decision mechanism

`Decision.subject_type` is extended with:

- `claim`
- `claim_evidence_link`

The corresponding subject IDs must use `clm-*` and `cel-*` grammar.

The Phase 2 `ResearchStateRegistry` remains responsible only for ResearchQuestion/Hypothesis subject resolution. It must tolerate newer Decision subject types without falsely reporting them as missing Phase 2 subjects. Claim/Link repository-level resolution belongs to Phase 3B.

### 6. Keep canonical state framework-neutral

`schemas/claim-evidence.schema.json` is the external contract. Pydantic models are the Python validation implementation and must not become the only definition of scientific state.

No graph database is canonical in Phase 3A. A future graph index may be derived from repository records.

## Consequences

### Positive

- evidence provenance can be recorded without prematurely asserting scientific meaning;
- contradictory evidence can coexist with supporting evidence without being suppressed;
- claim approval and evidence interpretation are separately inspectable in Git history;
- agents can propose scientific structure while human authority gates remain explicit;
- downstream manuscript generation can distinguish candidate claims, approved claims, raw evidence, and accepted interpretations;
- the representation supports later adversarial review and evidence-gap analysis.

### Costs

- the graph contains more first-class records than a simpler nested JSON representation;
- cross-object consistency requires a repository-level registry/audit layer in Phase 3B;
- authors must explicitly govern both substantive claims and material interpretation when those transitions become canonical.

These costs are accepted because the project prioritizes scientific auditability over minimal record count.

## Rejected alternatives

### Put `supports` / `contradicts` directly on Evidence

Rejected because evidence ingestion would then implicitly encode interpretation and blur the human authority boundary.

### Put evidence IDs directly on Claim as the only relation model

Rejected because this cannot represent contradictory evidence cleanly and does not provide an auditable lifecycle for interpretation.

### Give Evidence an `approved` lifecycle

Rejected because existence/provenance of evidence is distinct from confidence in or acceptance of an interpretation. Quality/confidence may be modeled later, but not as a substitute for claim/link governance.

### Make a graph database the canonical store

Rejected for Phase 3A. Repository JSON remains canonical; graph materializations should be reproducible derived state unless a later ADR changes that boundary.

## Deferred

Phase 3A does not define:

- repository persistence for Claims/Evidence/Links;
- cross-object reference resolution;
- Claim dependency cycle detection;
- Decision-history resolution for Claims/Links;
- automatic extraction from papers or experiment outputs;
- evidence strength/confidence scoring;
- statistical sufficiency judgments;
- novelty judgments;
- manuscript placement;
- graph/vector indexes.

Those are later bounded increments, beginning with Phase 3B repository-level persistence and audit.
